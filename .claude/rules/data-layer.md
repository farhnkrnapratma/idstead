# Data layer

- `@idstead/data` (`packages/data/src`) — the server-only data layer that pages, API handlers and jobs read through; only its D1 adapters exist (`packages/data/src/d1/`, the only place those tables are queried). The ports are grouped by file: `blog.ts` (`BlogRepository`, `CommentRepository`, `PostRenderStore`), `subscribers.ts` (`SubscriberRepository`, `NewsletterStore`), `activity.ts` (`FeedbackRecorder`, `AdminNotifier`, `ActivityLog`, `AdminActivityStore` with the dashboard, inbox, workspace, comment replies, report dismissals and subscriber counts, `AdminSettingsStore`), `legal.ts` (`LegalPageRepository`, `LegalPageWriter`), `adminAuthor.ts` (`AdminAuthorStore`, `AuthorWriter`), `resumeDocuments.ts` (`ResumeDocumentStore`, `OpenPgpKeyStore`), `adminPosts.ts` (`AdminPostStore`, `PostOperationStore`, `PostCleanupStore`, which return post UUIDs because they are admin-only), `siteData.ts` (`SiteDataStore` for the data export and delete-all), `identity.ts`, `ard.ts`, `lockout.ts` (salted key hashes only), `maintenance.ts` and `oidc.ts` (`OidcClientStore`, `OidcAuthStore` for "Sign in with Idstead": clients, grants, single-use codes and rotating refresh tokens, all stored as SHA-256 hashes). Public ports return the DTOs in `@idstead/domain/blog.ts` and `author.ts` without database IDs, and a post's storage location travels as an opaque `PostSource` handle. Post markdown and render files live in the `ASSET_BUCKET` R2 bucket under `content/` (`paths.ts`). Every store is built by `dataStores(platform, { fetch?, bannerUrls? })` in `packages/lib/src/server/data.ts`, the composition root and the only place that may import an adapter factory (`createD1*`; ESLint enforces this), from the `DB` and `ASSET_BUCKET` bindings (wrapped by `lazyBindings.ts` so they resolve on the first query). It returns `public` (the repositories plus the identity version reader; with `DATA_CACHE=1` the repositories are wrapped by `cachedRepositories()` from `packages/data/src/cache/`, which caches each read in the Workers Cache API (`server/resultCache.ts`) under a key made of the Worker version (`CF_VERSION_METADATA`), the domain's generation from `db_cache_generations` (bumped by triggers on every write) and the canonical arguments; post stats and recent comments are never cached) and `service` (everything else: `writers`, the admin, author and legal writers, newsletter, render, resume, ARD, lockout, maintenance, activity and OIDC stores). D1 has no row-level security, so callers must check their caller before using `service`: public writes are same-origin and Turnstile-gated, and admin endpoints verify the admin with `requireAdminAuth`/`blogAdmin` first. `publicRepositories(fetch)` and `serviceData(platform)` in `repositories.ts` are shorthands for `.public` and `.service`; the API worker uses `dataStores({ env }, { bannerUrls: false }).public` and, like the jobs worker, aliases `$app/env/*` to its own `src/appEnv.ts`. `@idstead/data` may depend on `@idstead/domain` only, browser code may not import it, and `@supabase/*` may be imported only by the auth modules (ESLint enforces all three). Admin browser code uses the Supabase client only for auth (`supabase.auth`), polls `/api/internal/admin/workspace` every 30 seconds and on focus for notifications, and reads and writes everything else through `/api/internal/admin/**`. `tests/contracts/` holds one contract suite per port group (`blogRepository`, `authorRepository`, `subscriberRepository`, `activity`, `adminPosts`, `adminAuthor`, `resumeDocuments`, `oidc`), run against the D1 adapters through the `bun:sqlite` D1 shim in `tests/support/d1.ts` (which applies the migrations and runs `batch()` as one transaction), plus adapter tests for the legal, site data, ARD index, identity version and login lockout stores.
- `packages/lib/src/supabase.ts` — the Supabase Auth client for admin browser code (and the auth fallback in `adminResume.ts`). Supabase is the auth provider only.
- `packages/lib/src/server/supabaseAdmin.ts` — the Supabase Auth admin client (verifies admin tokens, manages the admin user). **Server-only** — never import from a `.svelte` file or anything bundled for the browser. It never reads site data.
- Author data (profile, socials, funding, contact, resume entries, skills, project repo rules, active resume document and OpenPGP key, site URL) is read through `AuthorRepository` (`@idstead/data`, `repos.author`), which returns the `@idstead/domain/author.ts` DTOs without IDs and replaces the profile's identity version UUIDs with opaque tokens. The row mappers live in `@idstead/domain/author.ts`; `packages/lib/src/author.ts` only re-exports `@idstead/domain/author.ts`, and `authorApi.ts` shapes the public API output.
- `packages/data/d1/migrations/` — the D1 (SQLite) schema of the data layer, checked against the retired Postgres columns by `tests/d1Schema.test.ts` ([Database schema](../../docs/003-architecture/009-database-schema.md#d1-schema)); every schema change is a new D1 migration.
- `supabase/migrations/` — history of the retired Postgres schema, kept with the Supabase data until Stage 8; new schema changes go to `packages/data/d1/migrations/` only. Local dev servers share one local D1 database in `.wrangler/state/v3` (`bun run db:local` applies the migrations; `platformProxy.persist` in the Vite configs), so dev never writes production data.
- Comment moderation uses Llama Guard 3 through the web worker's `AI` binding. If the binding or the model call fails, the request is rejected with `BLOG_COMMENT_MODERATION_UNAVAILABLE` (503). `is_approved: false` means the AI held the comment back.
